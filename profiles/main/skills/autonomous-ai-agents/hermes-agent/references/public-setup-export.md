# Sharing a live Hermes setup safely

1. Locate the existing public setup repository and verify the active six-profile inventory separately from the default profile; stale root config is not evidence of the current chat's model. Read live configs only for explicitly allowlisted settings and never export credentials, user records or live scheduler contents.
2. Separate adapted installable templates from sanitized live references and optional extension source. Publish required package source with plugin shims or disclose missing dependencies; inventory dirty core paths and never imply a configuration snapshot supplies unshipped patches.
3. Exclude hidden skill-catalog caches as well as ordinary auth/state files. Scan historical commits separately: a new deletion does not purge public history, and a credential-pattern match is not proof of a valid key. Do not authenticate candidate credentials or rewrite history merely to obtain a clean current tree.
4. Make installation explicitly target a data ROOT, reject existing profile names and traversal, and copy only manifest-declared files. Validation that ignores generated caches must not be followed by recursive copying that includes them. Test the negative paths before implementing their fixes. Sanitize known owner addresses and identifiers without blanket-redacting upstream author/license email addresses; broad email replacement needlessly damages attribution. Exclude hidden catalog trees from observed skill counts as well as exported assets.
5. Preserve LF payload bytes across Windows and POSIX checkouts and verify a second clean Git checkout. A hash manifest can trigger secret-detector false positives when paths contain token/key names; allowlist only that generated manifest and independently recompute all its hashes, never broadly ignore source files.
6. Exercise a full temporary-home installation and the real Hermes CLI config readback without triggering account/model requests. Never point `HERMES_HOME` at a repository payload directory for this test. A packaged launcher may bootstrap a separate runtime for a new data root; use the already installed interpreter's real `python -m hermes_cli.main config get model --json` and `config path` against temporary installed profiles, verify every model/provider and resolved path, and report that boundary. Verify exact-head remote CI; honor any owner-reserved merge rule and stop at the published PR when it applies. Only after explicit merge authorization, merge the checked head and read back the default-branch tree and key files.
7. Coordinate takeover through the original source card, including concurrent automatic recovery workers. Do not create a duplicate assignment or repeatedly resume an unchanged failure. Use the native main-only triage settlement helper for verified takeover; if it records main ownership but completion is refused for missing PR metadata, read the source once and complete the now-ready main card with metadata.published_pr through the native tool. Do not replay the external work or weaken the PR acceptance gate.
8. Report self-review as self-review. If an independent review transition did not occur, do not label tests, source consultation or CI as independent specialist approval.
9. Run a temporary ad-hoc probe with the terminal workdir set to the ORIGINAL edited repository root, even when it checks a fresh published checkout elsewhere. The evidence classifier keys receipts by detected workspace; running the same passing probe from an unrecognized home directory does not record it for the edited root. Use a tempfile-created absolute hermes-verify- script path outside that root, inspect the terminal result for verification_evidence.kind=ad_hoc and status=passed, and clean the probe afterward. If the warning repeats, diagnose root/classification mismatch read-only instead of generating identical scripts, disabling the guard or writing synthetic ledger entries.
