# Token usage and cost reporting

## Procedure

1. Anchor the requested interval to the triggering message timestamp, not the time the investigation finishes. Use epoch timestamps for filtering and UTC for the report unless the requested local zone is verified. Do not infer the reporting zone from an inconsistent host clock or timezone label.
2. Resolve the actual Hermes installation root and requested profile homes. For an all-profile report, inspect the root/default database plus each installed profile's `state.db`; enumerate these shallowly rather than recursively scanning caches and backups. On Windows the deployed root can be `%LOCALAPPDATA%/hermes`, not `~/.hermes`.
3. Open SQLite read-only with `sqlite3.connect(path.as_uri() + '?mode=ro', uri=True)`. Inspect `sqlite_master` and `PRAGMA table_info(session_model_usage)` before constructing queries, since schemas evolve. Select only accounting fields, never conversation bodies or credentials.
4. Prefer timestamped per-call accounting if present. The verified fallback is `session_model_usage`: select buckets overlapping the interval with `last_seen >= start AND first_seen <= end`. Fields include `model`, `task`, `api_call_count`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `reasoning_tokens`, `first_seen`, `last_seen`, `estimated_cost_usd`, and `actual_cost_usd`.
5. Treat those rows as cumulative session/model/task buckets, not individual calls. Sum only buckets fully contained in the interval (`first_seen >= start AND last_seen <= end`). Separately disclose overlapping boundary buckets: including them overcounts older activity, while excluding them makes the result a confirmed minimum. Never prorate tokens by elapsed time. Do not filter on session start time: an old conversation can generate new model usage inside the interval.
6. Aggregate using code by profile, model, and optionally auxiliary `task`; include compression, title generation, and background reviews when recorded. Keep model aliases separate unless their mapping is verified. Explicitly mention profiles with no recorded in-window activity. Perform all groupings from the same captured rows so concurrent writes do not create mismatched totals.
7. Validate token semantics against the installed implementation when necessary. Locate it with `python -c "import hermes_state; print(hermes_state.__file__)"`; inspect the adjacent `agent/turn_usage.py` and canonical usage normalization. The verified accounting separates uncached input, cache reads, cache writes, output, and reasoning. Do not add reasoning to output again when it is an output subset, or call uncached input the entire prompt.
8. Report the window, data source, calls, uncached input, cache reads/writes, output, compact profile/model breakdowns, and the boundary caveat. On Discord use bullets rather than tables. Distinguish repeated cached-context traffic from fresh input; token throughput is not unique text volume.

## Diagnose and prevent runaway context use

- For a user-authorized behavioral audit, extend accounting with scoped per-session tool histories and bounded call logs. Count actual guard-denial tool results, repeated task-history fetches, unchanged-source rereads, tool-output character volume, first/peak prompt sizes and per-task call counts. Do not confuse normal prefix caching with fresh input or assume repetition proves unnecessary work.
- Inspect the effective merged profile config (`HERMES_HOME=<profile> ... load_config()`), not only raw YAML. A missing compression section can mean enabled ratio-only defaults with no absolute trigger, not disabled compression.
- Prefer supported config controls over core patches: `hermes -p PROFILE config set agent.max_turns N`, `compression.threshold_tokens N`, and `compression.protect_last_n N`. Choose thresholds above measured fixed prompt/tool overhead; preserve a useful summary and recent tail. A compression trigger is not a hard prompt/spend cap; summarization and cache rebuilds also cost tokens. Leave per-turn micro-compaction off unless its cache tradeoff has been measured.
- When fan-out is itself generating repeated work, main can disable `kanban.auto_decompose`; verify the installed watcher hot-reads it. Reducing main's `kanban.failure_limit` affects board-wide default counted failures, not only one profile; explicit per-task retry overrides and distinct protocol-violation budgets can still apply. Disclose that scope and do not present a default as a universal retry circuit breaker.
- Back up only the files being changed, retain work and isolation boundaries, and add concise behavioral rules: inspect supplied context before refetching task history, target unchanged-source reads, checkpoint bounded runs, and hand off genuine permission boundaries without workaround attempts. Do not weaken a guard to save calls.
- Verify saved config plus the installed compressor's trigger function without paid requests where feasible. Separately distinguish unit-level trigger validation, actual live summarization, and comparable post-change implementation savings. The latter requires a real follow-up task; do not claim an exact reduction before observing it.

## Per-assignment comparisons and self-serve checks

- For a Kanban assignment, map its recorded `owner_admitted` session ID to that assignee's `state.db`; a completed worker session gives a clean task total. Distinguish one planning assignment from the multiple model API calls/tool iterations inside it.
- Do not compare a worker's isolated assignment to main's entire ongoing conversation as if scopes match. Label main's thread snapshot explicitly, include separately recorded auxiliary tasks, and capture before/after baselines for future assignment-specific totals. Live cumulative buckets can include the accounting inquiry itself.
- For self-serve trends, verify `hermes insights --help` and use `hermes -p PROFILE insights --days N`. The installed `hermes usage --help` describes account limit/quota windows, not a cross-profile task-token ledger; do not conflate these views or launch paid benchmark calls to inspect existing accounting.
- Keep routine token reports lean: batch accounting-only SQLite reads, aggregate captured rows in code, separate uncached input/cache reads/cache writes/output, and export CSV when useful. Inspect bounded metadata rather than dumping full schemas or task histories once the schema and task-session mappings are known.

## Costs and evidence boundaries

- Label `estimated_cost_usd` as an estimate, not a verified bill. Zero recorded cost on an OAuth/subscription route does not prove zero economic cost or a complete cross-provider estimate.
- Do not infer remaining subscription quota from local token totals; provider quota rules and usage dashboards are separate evidence.
- If logs are needed, inspect bounded current/rotated profile logs around the interval rather than dumping them. Main-call usage lines can include `API call #... model=... provider=... in=... out=... total=... cache=... write=...`; confirm their timestamp zone and whether auxiliary calls are covered before treating logs as an exact ledger.
- If a long-running bucket prevents exact interval attribution, say so plainly. A verified lower bound with an excluded-bucket explanation is preferable to a falsely precise total.
