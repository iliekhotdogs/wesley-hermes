# Recovery evidence and transferable source patches

Use this procedure when resuming a crashed or capability-blocked implementation with preserved source and old receipts.

1. Read the original acceptance criteria and latest failure evidence once. Distinguish a process crash from an expired runtime cap; preserve the existing task, branch and worktree rather than spawning a duplicate.
2. Snapshot every intended changed source/test/doc path before further edits. Enumerate tracked diffs and explicitly include new regression files; plain `git diff` omits untracked files. Exclude dependencies, caches, credentials and session data.
3. Bind evidence to current raw file hashes. A passing receipt from an earlier patch does not certify later edits. Use the repository's canonical isolated runner, and assert every named test path exists before invoking it: some runners silently omit nonexistent paths.
4. Compare broader failures against the immutable base in a separate source snapshot, without stash/reset of user work. Record actual exit codes and full failure IDs. Use verbose pytest output when short summaries truncate identifiers; compare parsed sets, not counts or visual similarity alone. Keep failing receipts even when every failure reproduces on base.
5. Inspect the complete diff and map every changed path to the user's enumerated scope. Distinguish tested local repairs, partially repaired reports, baseline non-applicability, feature/policy decisions and unreproduced external environments. Never turn closed-as-duplicate into verified resolution.
6. Use locked worktree-local test dependencies and caches. Prefer direct local executables or `npm exec --no` during validation so a missing binary cannot trigger an implicit install into the default exec cache. Read back versions after installation; preserve failed attempts and disclose incidental writes.
7. Export tracked plus explicitly permitted new-file diffs without staging or committing. Check whitespace and reverse applicability in the repaired tree. Independently forward-check and apply the patch to affected baseline files, then compare every resulting Git-canonical blob to the repaired tree. Normalize BOTH sides through the same Git attributes; comparing canonical LF to raw Windows CRLF creates false mismatches.
8. Build a report/patch/source/evidence bundle from an explicit manifest; reopen it and verify member uniqueness, manifest hashes and exact patch bytes. Include real command outputs and limitations, not just a PASS label. Preserve old artifacts as historical; deliver new names for the current export.
9. Attach durable deliverables before claiming recovery complete. Complete the source only when its actual acceptance criteria permit the remaining dispositions, and read back the exact source card after settlement. Keep a source incomplete when independently feasible repairs or a genuine blocker still prevent acceptance.
10. For a main-only source settlement helper that accepts only a summary, copy the verified deliverables into that source workspace and name their exact native absolute paths in the summary. Native completion can then discover and preserve them instead of automatically walking/compressing a large undeclared source/dependency tree. A timeout may leave an intermediate ownership/status transition; read back the source and check for a live helper process before making one concrete corrected retry. Never replay the implementation or external mutations merely to repair its completion message.

11. In an explicitly assigned main recovery worker, a source-card CLI comment/unblock can inherit `HERMES_DELEGATED_CHILD_CONTEXT` and refuse mutation even though main has administrative authorization. For those exact authorized source-card operations only, run the CLI in a single process with that variable removed (`env -u HERMES_DELEGATED_CHILD_CONTEXT hermes kanban ...`); never change global environment, permissions, or specialist boundaries. Read back the exact source afterward. Use the existing main-only settlement helper for verified completion, not an early completion merely to escape this guard.

A local evidence gate certifies only its declared current hashes and checks. It is never a full-suite, CI, deployed-system, independent-review or all-issues-fixed certificate.
