# Google Health API alongside Workspace OAuth

Use this when the user has already configured a Google OAuth project for Gmail/Calendar and wants Fitbit/Google Health data in Hermes. Follow the SKILL.md rule on **Extending an existing OAuth project** first. The Health grant is a separate token and may belong to a different Google account.

1. Ask the user to verify that the named tracker appears under Google Health mobile app → Connections and shows a recent last-sync time; a live sensor reading on the tracker alone proves neither pairing nor cloud sync. Google's OAuth consent can authenticate an account with a linked Health profile but no tracker. In the same Cloud project as the Desktop OAuth client, enable Google Health API, declare the needed scopes under Data Access, and add the Health account under Audience → Test users if the app is in Testing. Do not restart or revoke the Workspace grant.
2. Request only the relevant read-only scopes via a local Desktop-client PKCE loopback flow. Steps/activity: `https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly`; sleep: `https://www.googleapis.com/auth/googlehealth.sleep.readonly`; heart rate: `https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly`. Select fewer if the user wants fewer metrics. Console Data Access configuration does **not** update an existing user token.
3. Save the Health grant in a separate credential file in the authorized local profile, never `google_token.json`. Keep authorization URL, callback code, refresh token, and client secret out of chat and logs. Let the user operate Google's browser consent. Do not claim connection merely because the local listener accepted a callback.
4. Verify two separate claims. First, `GET https://health.googleapis.com/v4/users/me/identity` must identify a linked Health profile and `GET /v4/users/me/dataTypes/steps/dataPoints?pageSize=1` (or a chosen metric) must authorize successfully; a 200 `{}` is an empty protobuf page, so use `body.get("dataPoints", [])` after shape validation. Second, check actual tracker provenance: query steps with `dataSourceFamily=users/me/dataSourceFamilies/google-wearables` and check both `heart-rate` and `daily-resting-heart-rate` sample endpoints with the granted health-metrics scope, optionally filtering a recent sample-time window. Compare against all-source steps. If wearable-only steps and heart metrics are empty while all-source steps exist, label the latter as non-verified tracker data; do not describe those *records* as tracker-sourced, but do not conclude the tracker is unpaired. Calories or a live wrist reading can coexist with an empty heart-rate API: each metric has its own sync path. Ask whether historical heart-rate measurements appear in the phone app; if they do, compare the app's Google account with the one selected at OAuth consent without soliciting an email in a public chat. The Health `identity` response confirms a linked profile but does not expose the account email, and tokeninfo for health-only scopes need not reveal it. Query both `heart-rate` (with a bounded recent `heart_rate.sample_time.physical_time` filter) and `daily-resting-heart-rate`; if necessary compare a daily rollup or `dataPoints:reconcile` to distinguish query-shape mistakes from source availability. An empty 200 on these paths is evidence of missing API-visible records, not proof of absent sensor, pairing, or app sync. If the user confirms historical heart-rate graph and the same account, stop suggesting pairing or OAuth repeats; report the remaining app-versus-API discrepancy as unresolved, check documented sync latency, and offer support escalation only if it persists. Do not claim a provider bug without evidence. Do not rerun OAuth unless an account mismatch or consent issue is verified. Report only status/source classification and record counts in public chat, never raw health values or identifiers.
5. Test token isolation, requested scopes, identity rejection, redacted output, and the empty-page response with mocked responses before live authorization. Keep the live result pending until the user actually consents; a mock pass is not an end-to-end connection.

## Daily interpretation and reporting

1. Collect in the user's named timezone: use a completed civil day for steps and the following wake-up morning for overnight sleep. Query the `steps` daily-rollup endpoint using a one-day half-open civil range; distinguish an empty response from a measured zero. Compute a prior-days median only from available days, and compute percentage changes in code rather than asking the language model to do arithmetic.
2. Fetch sleep sessions by their civil end time; if stage intervals exist, sum only `LIGHT`, `DEEP`, and `REM` interval durations. Do not subtract overlapping short awakenings a second time, and do not present time-in-bed as sleep duration. If stages are missing, say duration unavailable. Probe heart-rate availability on **each scheduled run**, not once at connector setup: query a bounded recent `heart-rate` sample window and a daily `daily-resting-heart-rate` record. Include an explicitly labelled resting BPM only when the matching date's record exists; a sample's mere presence is not an average or a safe interpreted value. Mock both empty and newly populated API responses so a report does not remain permanently hardcoded “unavailable” after sync improves.
3. Pass an aggregate-only, bounded JSON payload to the reporting agent. Require date/coverage, a comparison conditional on valid baseline, one or two gentle actionable suggestions, and clear non-medical framing. Never infer a condition from a single day or fabricate an unavailable metric. Distinguish phone/third-party steps from verified tracker steps in the report; otherwise a working account API can mislabel another source as wearable activity. Keep raw values out of public channels and deliver privately after verifying the recipient ID.
4. Test the collector with mocked empty pages, missing data, civil-date boundaries, and sleep-stage intervals; then perform a live API read without printing raw values in a public transcript. Verify the first scheduled report in the exact private destination before reporting recurring delivery success. See the `discord-scheduled-delivery` skill for cron delivery mechanics.

References: https://developers.google.com/health/setup , https://developers.google.com/health/scopes , https://developers.google.com/health/data-types . Check current docs for endpoint/schema changes rather than assuming this note is timeless.
