# Video content analysis

Analyze a local video with a Whisper transcript and sampled frames; use video analysis for motion when needed. Disclose sampling gaps only when they affect the answer; speech and on-screen text are the reliable parts of the frame-and-transcript method.

## Routing and interface checks

This skill lives only in main's profile and requires host-level yt-dlp/ffmpeg/faster_whisper. Do not delegate a reel/video-analysis task to builder (or any Docker-sandboxed specialist) expecting it to run this skill: the Docker sandbox has no yt-dlp/ffmpeg and cannot pip-install faster_whisper (MAIN_REQUIRED), and the skill itself is not loaded into that profile, so the task will just bounce back blocked. Main should run the retrieval/ffmpeg/Whisper steps itself with its own terminal, then hand only the resulting summary/verdict-writing (not the raw extraction) to a specialist if delegation is wanted at all.

Keep link submission as the user's default workflow: retrieve and prepare media behind the scenes rather than requiring the user to download, transcribe, or choose an analysis model. Use the existing Drive inbox only when link retrieval cannot provide the media.

Before routing videos to another model's CLI, verify the exact interface's support separately for video URLs, local video files, audio, and images. Do not infer CLI capabilities from the vendor's chat app or API; those surfaces may expose different modalities and entitlements. A fetched caption or webpage is not evidence that the model watched the video.

Test a small authorized clip with known spoken and visual events before claiming end-to-end video analysis. A failed link test does not establish whether local-file input works. Route to the alternative only when testing demonstrates better coverage, useful independent analysis, or worthwhile quota savings; feeding it the same transcript and sampled frames is a second opinion, not native video understanding. Keep unverified candidates out of default routing and preserve the user's link-first interface if a backend changes.

## 1. Get the file local (pick the first that fits)
- **Drive inbox (verified route):** user uploads to a Drive folder (no size limit, works from phone, avoids Discord's ~10 MB free upload cap). List with `google_api.py drive search "'<folderId>' in parents and trashed=false" --raw-query --max 50` (returns id/name/modifiedTime; filenames are opaque hashes, so identify videos by content), download with `google_api.py drive download <fileId> --output <path>`. For several videos, loop download into one scratch dir as v1..vN.mp4 and process them in one batch.
  - A folder link alone grants nothing: a 404 "File not found" means the folder is not shared with the authorized account. Find the account with `drive.about().get(fields="user(emailAddress)")` and ask the user to share the folder (Editor) with that address. Never assume the authorized account is the user's own.
  - The user must ping in chat after uploading; do not poll.
- **Discord attachment:** works if small enough; analyze the cached local path.
- **Public Instagram `/reel/` link:** First try `~/.local/bin/yt-dlp.exe -o in.mp4 "<url>"` in a fresh scratch dir (install: `uv tool install yt-dlp`; call the exe by full path). If Instagram returns an empty media response, try the public `https://www.instagram.com/reel/<shortcode>/embed/captioned/` page with `curl -L -A 'Mozilla/5.0' -o embed.html <embed-url>` before asking for a Drive upload. Its embedded `video_url` may be multiply backslash-escaped: extract the full `https:\\/\\/...mp4?...` string from the page, replace `\\u0025` with `%` and strip remaining backslashes, then HTML-unescape and download with a browser User-Agent and Instagram Referer. Probe the downloaded file with `ffprobe` before analyzing; the embed can expose a directly fetchable video even when yt-dlp cannot parse the post. If neither public route yields media, use the Drive inbox; do not treat one extractor failure as proof the post is private.
- **Instagram `/p/` carousel (may mix stills and videos):** Run `yt-dlp -J --flat-playlist <url>` for caption/uploader and per-entry media URLs; some entries may be `null` even when the post has video. To read the slides: `curl -sL -A "Mozilla/5.0" https://www.instagram.com/p/<code>/embed/captioned/ -o e.html`, extract every `display_url` from the page (the JSON is multiply backslash-escaped; match `re.findall(r'display_url\\":\\"(.*?)\\"', html_text)`, strip all backslashes, `html.unescape`, and deduplicate URLs in order), download each with a browser User-Agent. Normalize each image to the same dimensions *before* tiling: `for i in 0 1 ...; do ffmpeg -v error -y -i "s$i.jpg" -vf 'scale=360:480' -frames:v 1 "t$i.png"; done`; then `ffmpeg -v error -y -start_number 0 -i t%d.png -vf 'tile=3x3:nb_frames=8' -frames:v 1 sheet.png` (adjust count/layout). Directly tiling mixed-size JPEGs can produce blank cells because ffmpeg's image sequence assumes uniform dimensions. Read the sheet with `vision_analyze`; for video entries, download/transcribe or explicitly say their clips were not analyzed. The embed page works without a browser.
- On Windows, give native programs an absolute `C:/...` output path from the start, including yt-dlp's `-o` template; a POSIX `/tmp/...` output template can be interpreted as `C:\\tmp\\...` by the native executable while later shell tools inspect a different directory. Resolve the actual directory with `pwd -W` before passing it to ffmpeg or Python.
- A bare filename with no directory in yt-dlp's `-o` (e.g. `-o reel.mp4`) is not safe either: the native Windows build can silently drop it at the current drive's root-level `C:\tmp\` instead of bash's `/tmp` or `$TMPDIR`. If a downloaded file isn't where expected, check `/c/tmp/<name>` before assuming the download failed — but always prefer passing a full resolved `-o C:/.../name.mp4` path so this ambiguity never comes up.
- When writing a helper script (e.g. the Whisper transcribe script) with the `write_file` tool for a terminal command to run next, do not reuse the bash `$TMPDIR`/scratch path by feel — `write_file`'s path resolution and the terminal's cwd can disagree on Windows, landing the script in a different directory than the one the shell session is in. Run `pwd -W` in terminal first, then pass that exact native path to `write_file`, so the later `python -I script.py` finds the file on the first try.

## 2. Analyze (work in scratch dir, not the Drive folder)
Raw social videos can be 100+ MB for ~2.5 min; do not feed them whole to `video_analyze`. Derive small artifacts instead:
```
ffmpeg -v error -y -i in.mp4 -vf "scale=360:-2,fps=1/10" -q:v 5 a_%02d.jpg   # 1 frame / 10 s
ffmpeg -v error -y -i in.mp4 -vn -ac 1 -ar 16000 a.wav
ffmpeg -v error -y -framerate 1 -i a_%02d.jpg -vf tile=4x4 -frames:v 1 a_sheet.jpg  # contact sheet
```
- Use the `%02d` sequence pattern for ffmpeg input; `-pattern_type glob` fails on Windows builds.
- Transcribe: `WhisperModel("base",device="cpu",compute_type="int8").transcribe("a.wav", vad_filter=True)` from `faster_whisper` (CPU is fine; ~2.5 min audio finishes inside a tool timeout). Run it from a script file with `python -I`, load the model once and loop all clips, and redirect output to a file (`> tr.txt`) then `read_file` it: piping through `tail` or reading the background-completion notification truncates long transcripts.
- A multi-video ffmpeg+Whisper run exceeds the 600 s foreground cap and is auto-promoted to a background process; wait on it with `process_manage` (a deferred tool: call it via `tool_call`, it is not a direct tool). Wait is clamped to ~180 s per call, so re-wait.
- Clips that are consecutive parts of one talk (transcript ends mid-sentence, same speaker/setting) should be rated and reported together as a series.
- Read each contact sheet once with `vision_analyze` (one call per ~16 frames instead of 16 calls). Tighten fps or crop with `region` only if on-screen text (whiteboards, slides) must be read.
- Burned-in captions in frames corroborate the transcript; mention if they agree.

## 3. Report
Give: what the video is (setting, speaker, source watermark), a structured summary, and relevant limits (sampling gaps, unreadable small text). Keep a bare-link response concise; mention token cost only if asked or material to the decision. Offer follow-ups rather than doing them unasked. For a bare social link, identify each media type before describing it; summarize the post rather than assuming all slides are stills or all are videos. When a carousel promotes a benchmark, check the cited primary source before repeating the headline, distinguish task-specific company-run tests from general-purpose model performance, and state when embedded clips were not transcribed. If the user then asks what went wrong or requests a diagnosis, examine the immediately preceding analysis for a concrete likely mismatch and explain it first; ask a narrow clarifying question only if the target remains genuinely indeterminate. A generic menu of possible problems evades the requested diagnosis.

When the user asks which videos are "worth looking into": rate each out of 10 with pros and cons and a one-line verdict, judged against the user's actual setup (Hermes multi-profile agents, 8 GB RAM / no GPU PC, hosted APIs), then end with a short ordered "what I'd do". Flag engagement-bait roundups and claims that cannot run on the user's hardware.

## 4. Follow-ups on tools a video mentions
Video spoken names are often garbled by Whisper (e.g. a product heard as "pits a bot" was really Pizza Bot; "Artemis", "Terneri Bonsai" were right only after searching). Resolve each name with `web_search`, confirm it is real from the project's own repo/blog, then rate it per tool. When asked to summarize docs, `web_extract` the repo README / launch post; extracted pages are truncated head+tail, so `search_files`/`read_file` the saved cache path for the omitted middle. Say plainly that ratings come from docs and search results, not from installing or testing, and name which tools were only judged from slide/caption text.

When the user asks for deeper research after a reel summary, move beyond repeating the launch post: inspect the primary repository/docs, the benchmark's model, hardware, storage and workload, deployment requirements, maintenance state, and how the approach compares to the user's existing stack. Distinguish idle/suspended-agent memory from active model inference or throughput; a headline extrapolated from a benchmark is not a demonstrated end-to-end workload on the named consumer device. Give a practical adopt/watch/skip recommendation with what evidence would change it. For promo reels about Hermes releases, compare the claimed version against the local engine (`hermes --version`, release changelog) first: claims are often already shipped in the installed version, which is the useful finding. For mobile-client TestFlight reels, read the app title and description from a full-resolution frame, then independently verify the exact invite and developer against an official source before calling it official or connecting it to the user's gateway. Distinguish the value of a mobile companion from the trustworthiness of a comment-for-link reel; third-party clients may use similar branding and a beta's remote access/tool approvals have substantial permissions. Promo reels/carousels are "comment X for my free guide" lead-gen; rate them low as media and pull out only the one or two items worth acting on.
