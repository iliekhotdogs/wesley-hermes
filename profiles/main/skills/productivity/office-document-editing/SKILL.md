# Office document editing

For READING/extracting text only, use `ocr-and-documents` instead, or simpler still: Hermes' `read_file` tool auto-extracts text from pptx/docx/xlsx with paragraph/line numbers — call it directly on the native file path before reaching for python-pptx/docx just to inspect content. This skill is for WRITING changes back into an existing Office file (where you do need python-pptx/docx to target shapes/runs).

## Procedure

1. Locate the uploaded file path (Hermes gives it under `cache/documents/native-inputs/...`). Never edit it in place — write output to a new path, e.g. `cache/scratch/<name>_Filled.pptx`, and hand that back to the user.
2. Ensure the library is installed in the interpreter the `terminal` tool actually runs (`python3 -m pip install --quiet python-pptx` / `python-docx` / `openpyxl`). `ModuleNotFoundError` here is just a missing install, not a tool limitation — install and retry once.
3. First **inspect structure before editing**: dump every shape's `shape_id`, `name`, and current text (pptx) or every paragraph/cell (docx/xlsx). Placeholder templates often already have some fields filled in by the user — read current text first so you fill only the blanks/bracketed placeholders and don't clobber their edits.
4. Write the edit script to a file with `write_file` (or the `patch` tool), then run it with `terminal`. Do NOT build multi-line Python inside a bash heredoc passed through the `terminal` tool's `command` string — nested quoting (apostrophes in content, `'EOF'` delimiters) breaks the shell parse. Always stage the script as its own `.py` file first.
5. **Preserving formatting when replacing text in a run-based format (pptx/docx):** don't just set `shape.text_frame.text = "..."` — that collapses multi-run formatting. Instead, grab the font properties (bold/italic/size/name/color) from the *existing* first run of the target paragraph, clear the paragraph's runs, then add new runs/paragraphs and re-apply those captured properties. This keeps the template's visual style on the filled-in text.
6. Target edits by stable `shape_id` (or cell address), not by matching old placeholder text — placeholder brackets are easy to mistype and matching by ID is exact. `shape_id` numbering is per-FILE, not per-template: two pptx files built from the "same" template (e.g. the original blank template vs. the user's later re-export) can assign completely different shape_ids to the same visual shape. Always re-dump shape_ids from the exact file you are about to edit — never reuse ids read from a different upload, even one that looks identical.
7. If the user re-uploads a file they personally edited, that upload is the new base — reapply any pending fixes on top of THEIR file, not your last-generated version. Sending back your older version silently discards their work and they will notice.
8. To copy a whole slide (with its shapes/formatting) from one Presentation into another: `add_slide()` a blank layout in the target, strip the layout's placeholder shapes, then `deepcopy` each shape's `_element` from the source slide into the new slide's `shapes._spTree`. To reposition it, splice `prs.slides._sldIdLst` (remove/insert the `sldId` element) rather than looking for a `move_slide` API — python-pptx has none.
9. To make text visually pop without a full redesign, it's often enough to bold/color-code the label runs (e.g. "Result:") and the value that follows, pulled from the existing accent colors already used elsewhere on the slide/deck — cheaper and more consistent than inventing new icons or layouts, and satisfies "make it more visually appealing" asks. The same technique works on run-on body text with no formatting at all: split it into an action line + a bold accent-colored outcome/target line for instant hierarchy.
10. After saving, verify programmatically: reopen the saved output file and assert expected strings landed on the right slide/paragraph/cell (don't just trust the script ran without error — actually reload and check content). Report the verification as what it is: an ad-hoc check script for this change, not a claim of a pre-existing test suite.
11. Leave genuinely-optional fields (e.g. "[Optional: your LinkedIn or email]") as placeholders rather than inventing a value — only fill fields that have a concrete answer.
12. To add a new row/entry to a repeating list layout (e.g. one more reference on a references slide), `deepcopy` the `_element` of an existing row's shape(s), append to `shapes._spTree`, then reposition by setting `.top`/`.left` on the new shapes — same pattern as whole-slide copying, just at shape granularity. Re-fetch the appended shapes as `list(slide.shapes)[-N:]` since they land at the end of the shape order.
