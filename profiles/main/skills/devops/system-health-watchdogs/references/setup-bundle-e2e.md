# Updating setup bundles and testing a standalone watchdog

- Distinguish a setup/export repository from the Hermes framework before updating a PC. Preserve the framework's dirty patches and untracked implementation files; apply reviewed compatible payloads instead of replacing the engine with an export tree.
- Discover the remote default branch with `git ls-remote --symref ... HEAD`; do not assume `main`. Validate manifest hashes and execute bundle tests before installing into a fresh isolated data root.
- Do not install an export over existing profiles. Reconcile role/security/memory changes individually, preserve account credentials and existing scheduler definitions, and record local adaptations separately from the source commit.
- Treat `Path.resolve()` as potentially leaving the Hermes tree on Windows. Scripts may live behind a directory junction; resolve configuration from the explicitly owning `HERMES_HOME`, not the resolved script's parent. Test required guild/config bindings by importing deployed code without executing cleanup mutations.
- Exercise `hermes cron create --no-agent --script ... --deliver local` plus its real run/tick path with a disposable test home. A wrapper may invoke the exact deployed standalone watchdog against isolated health-state fixtures and load the existing authorized webhook privately. Do not fake a network response or stop a production gateway to create an incident.
- A watchdog's health-incident exit code may be nonzero even when alert delivery succeeds. A test wrapper may accept the documented expected incident code only after checking state persisted following delivery; distinguish this from the cron job's successful integration-test result.
- Record the durable cron execution row and verify a unique TEST marker, webhook ID, exact message ID, channel name and guild through Discord GET. Webhook HTTP success alone is not destination verification. Preserve a permalink and secret-free receipt, never the webhook token.
- Use a profile-scoped standalone launcher and an independent OS task for ongoing gateway alerts. Load the existing secret from the owning profile and inject explicit home/executable/profile only into that process. Verify stored task action, repetition, non-overlap policy and actual completion result.
- Remove the disposable cron job and read back the empty test schedule. Preserve its execution DB and sanitized evidence separately. Existing production job files can change due to runtime bookkeeping; compare stable definitions rather than demanding byte-identical hashes.
- Coordinate with automatic main recovery workers through the original card. Preserve and independently read existing receipts instead of repeating deployments, alerts or restarts for a second notification.
