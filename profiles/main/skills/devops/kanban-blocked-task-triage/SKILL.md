# Kanban blocked-task triage and prevention

## Procedure
1. List: `kanban_list status=blocked` and `status=triage`. In a worker/terminal use `hermes kanban list --status blocked --json` and `hermes kanban show <id>`; grep the show output for block/reason/error rather than reading whole cards.
2. Cluster by CAUSE, not by card. Typical classes: (a) Docker worker cannot see host paths; (b) stale cards whose cause is gone (model swaps, answered questions); (c) task given to the wrong specialist (lib/speedy asked to implement, out of iteration budget); (d) external consent (Google OAuth `invalid_grant`, cloud MCP sign-in) that only the user can do; (e) work finished but card never settled; (f) gateway-disconnect crashes.
3. Propose per-card fixes AND broad prevention, then wait for the user's go-ahead.
4. Implement prevention one item at a time. If the user says do not rerun blocked jobs, change only tooling/config/cron; do not unblock, archive, or resume cards unless separately approved.
5. Finish with a summary: what changed, how it was tested, what was NOT done and why, what still needs the user.

## Prevention tooling (build once, reuse)
- Docker workers (builder, cowsearcher) only see `C:/Users/YOUR_USER/hermes-workspaces/<profile>` as `/workspace`. Stage inputs with `profiles/main/scripts/stage_task_inputs.py <profile> <task_id> <paths>`; it prints container paths and refuses secret-looking paths. Never hand a worker host paths.
- When a `dir`-kind task's `workspace_path` is a SUBFOLDER of that profile root (e.g. `.../hermes-workspaces/builder/econ-midterm`), the container still only sees the profile root at `/workspace` — the in-container path is `/workspace/<subfolder-name>`, NOT the full absolute host path re-rooted (a worker that tries `/workspace/Users/YOUR_USER/hermes-workspaces/builder/<subfolder>` will get "not found" and may wrongly report a capability block). Before telling a blocked worker to retry, verify the real in-container path yourself with `docker run --rm -v "C:/Users/YOUR_USER/hermes-workspaces/<profile>:/workspace" <image> ls /workspace/<subfolder>` and give it that exact path in your unblock comment.
- Cap the recovery chain in `profiles/cron/scripts/kanban_recovery.py`: skip cards titled `Recover specialist assignment:` or created by `cron:main-recovery-router`, so recovery cards cannot spawn recovery cards.
- Weekly read-only sweep: `profiles/main/scripts/stale_card_sweep.py` (blocked >7d plus Google refresh-token check), registered as a no-agent cron job (`hermes cron create --no-agent --script <name> --deliver origin "0 9 * * 1"`). Cron scripts live under the profile's `scripts/` dir and print nothing when healthy.

## Pitfalls
- Regexes with Windows backslashes crash or mis-match; normalise with `Path.as_posix()` and match `/` only. Use `[.]env` not `\.env` when editing through heredoc/sed layers that eat escapes; test the pattern on one positive and one negative sample.
- Core-engine behaviours (dispatcher auto-resume on gateway disconnect, creation-time path validation) need a plugin/hook; do not patch the pinned engine. Plugin hooks are observer-only (no pre-create hook): `kanban_task_claimed` fires in the dispatcher just before spawn and `kanban_task_blocked` fires with `reason`. Use them to stage inputs and add comments, not to veto.
- Local guard plugin: `profiles/main/plugins/kanban-sandbox-guard` (enabled under `plugins.enabled` in main's config.yaml). On claim of a builder/cowsearcher card it stages any host paths found in title/body and comments once (marker `[sandbox-guard]` keeps it idempotent); on a block reason containing "Gateway disconnected" it comments that the outcome is unknown, so check side effects before resuming once. It never auto-resumes, because a disconnected turn may have already run side effects.
- Kanban DB access from a plugin/script: `from hermes_cli import kanban_db as kb` plus `from hermes_cli import kanban_db_connect as kbc; with kbc.connect_closing(board=...) as conn:`; use `kb.get_task`, `kb.list_comments`, `kb.add_comment`. Verify plugin logic with mocked kb modules before live use; enable check: `hermes plugins list`.
- Escaping layers (bash heredoc, python -c, sed) corrupt backslashes in regexes; write plugin files with the patch/write_file tools and read back the exact line.
- Closing a done-but-blocked card: `python profiles/cron/scripts/kanban_recovery.py settle <id> --summary "..."` then `hermes kanban archive <ids...>`. Archive stale cards only when the user approves; leave cards whose work was never done (or that need user consent) open.
- `hermes kanban archive` takes only task-id positional args, no `--reason`/`--summary` flag (it errors "unrecognized arguments"); post the reason as a `kanban_comment` on each card first, then run the bare `archive <ids...>`.
- When asked to delete/archive cards older than an age cutoff, get `date +%s` for "now", subtract the window in seconds, and compare against each card's `created_at` (from `kanban_show`) before archiving — do not eyeball "days ago" strings, and do not archive a card just because it is capability-blocked if it is inside the window.
- There is no tunable "blocking parameter" to adjust in Kanban — card status transitions are behavioral (a worker legitimately hits a MAIN_REQUIRED boundary and blocks), not governed by a config knob. When a user asks to "find the root problem and adjust blocking parameters," the real fix is almost always: (a) confirm the weekly `stale_card_sweep.py` cron is active (`hermes cron list`) so stale blocks surface to main on a cadence instead of sitting for weeks, and (b) check whether cards were specced assuming host/credential access the assignee's sandbox structurally can't have — route those to main from the start rather than treating the resulting block as a bug to fix.
- `kanban_complete` refuses a card "running under a live worker claim" — fall back to `hermes kanban complete --force <id> --summary "..."` via terminal. It also refuses a parent whose children (including auto-decomposed duplicates created mid-task) aren't done/archived yet: force-complete every child first, then the parent. If a specialist's task got auto-decomposed into child cards duplicating work main already finished directly, force-complete each child with a one-line pointer to the parent's result before completing the parent.
- A fresh `docker exec` into a profile's named container (e.g. `hermes-builder`) does NOT share that profile's own per-task ephemeral workspace mount — its terminal tool's `/workspace` is bound in a private mount namespace set up per call, invisible to a new exec session (`nsenter -t 1 -m` also fails, no privilege). When main must perform a privileged step (e.g. `pip`/`uv install`, blocked for every role but main) inside that container, do the whole remaining step there too rather than fight the namespace: find a host-backed, exec-capable, non-tmpfs mount inside the container (e.g. `/builder-home`; check via `mount | grep -v tmpfs` and avoid noexec entries) and run the install plus the actual work on that path, then report results back on the card — don't expect a later `docker exec` to see files written to `/workspace` or `/tmp`.
- `docker cp` into a container preserves the source (often root) ownership, so a following write as the container's unprivileged user gets `PermissionError`. Fix by `cp -r` the copied tree into a fresh directory as the container's own user (or `chown -R $(id -u):$(id -g)` the copied tree) rather than writing into the `docker cp` destination directly.
- Never forward a host secret (API key) as an env var into a shared/long-lived Docker worker container — that violates the no-credential-forwarding sandbox policy even when main is doing the exec. If a step needs a secret (e.g. an LLM API key for a one-off tool), run that step in main's own host environment (e.g. a throwaway `python -m venv` + pip install) instead of inside the worker container.
- NVIDIA NIM (and other OpenAI-compatible providers) rotate/retire model IDs without notice — a previously-working model id can return `410`. Before trusting a hardcoded model name, hit `GET {base_url}/models` with the API key and grep for the family you want (e.g. `nemotron`) to get current valid ids.
- `cronjob_manage` (and other native model-tool wrappers like Drive/Docs API calls) is gated MAIN_REQUIRED for specialist profiles — a specialist escalating "tool_describe denied MAIN_REQUIRED" for a routine Google Workspace write or a cron job creation is not a dead end, it's a handoff: main has full access to these tools and should just perform the step itself (e.g. create the recurring job, do the Drive `files().update(addParents/removeParents)` move) directly, verify it, then settle/comment on the card. Do not bounce it back to the specialist or ask the user to grant access.
- Probe a token before telling the user to re-authorize; a stale card's token problem may already be gone.
- Keep lib/speedy off implementation; small memory records go straight to main.
- A Docker worker's approval prompt for writing a protected instruction file (e.g. `SOUL.md`, `AGENTS.md`) has no live human-delivery path inside that sandbox — it just times out waiting for a response nothing can supply, every time, regardless of prior user approval. Do not have the specialist retry it or try an alternate tool/path. Main should write the protected file directly on the host with its own authorized tools (back it up first) rather than loop the worker through the same dead approval gate again.
- `write_file`'s stale-pagination guard ("was last read with offset/limit pagination") can misfire and block even a correct, freshly-read overwrite. Do not retry `write_file` unchanged — switch to `patch` with exact `old_string`/`new_string` spans, which the guard does not block, and which also preserves any content outside the edited span.
- The auto-decomposer can spray several redundant sibling/child cards off one blocked parent (e.g. "draft candidate", "record source inventory", "integrate candidates" all off the same root cause). Once you've resolved the actual root cause directly, sweep `kanban_list status=blocked` and `status=triage` for the whole cluster and close every sibling with one "superseded by <parent/decision>" comment + archive, rather than reacting to each wake notification as a fresh problem.
