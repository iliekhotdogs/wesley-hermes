# Roblox experience development

## When to Use
Use for Roblox opportunity research, Rojo/Luau prototypes, Studio handoffs, or a gated decision about further game development. Pair with story-loop for cross-profile handoffs and explicit stage approvals.

## Procedure
1. Inspect the named project folder, instructions, assets, code, and available toolchain before creating anything. If a path from another OS is absent, locate the project by distinctive source files, then verify its Git remote, branch, working-tree status, and baseline before choosing a canonical folder; never silently substitute a same-named scratch copy. Keep deliverables—including research, built place files, local test logs, and gate reports—in the owner's specified or verified canonical folder. Preserve existing work; when a new game is requested alongside an existing prototype, use a distinct project subfolder instead of replacing the old game. State `Done means:` for the current stage and stop at its gate unless the owner explicitly authorizes the next build stage; reflect later changes to team size or rules in the implementation spec before dispatch.
2. Frame player, promise, distinctive interaction, solo viability, device context, three falsifying assumptions, and two lower-burden alternatives. Label observation, official documentation, hypothesis, and unknown separately. Consult current Roblox Creator Hub pages and record URLs/access dates for platform claims.
3. For competitor research, prefer direct alternatives and a few adjacent onboarding/social/replay examples. Record each experience's URL/date and evidence mode (listing, video, or hands-on); do not turn public activity into retention, revenue, or quality claims. If a listing has no imagery, Store prices, or first-session access, mark each unknown rather than filling from plausible mechanics. Synthesize design risks as *hypotheses* unless players actually exhibited them.
4. Before polished content, build a disposable single-route/single-object core risk probe. Put pure decision rules in a Luau module and write Lune assertions before implementing them; keep Roblox services in the runtime scripts. Use Rojo build, StyLua check, Selene with `std = "roblox"`, and Lune tests; retain the real command output. When adding a runtime module, register it in the project's source/place structure assertion as well as the Rojo mapping; rebuild and compare its embedded Source to the file so a green unit test cannot conceal an unlisted or stale module. Check the built place contains the intended server/client/module scripts. For a complete match loop, add an end-to-end Lune harness that loads the server and client scripts from the built place, drives a simulated human through match completion, replay, and departure, and asserts no script errors; this catches integration gaps that isolated rule/HUD tests miss. Keep the harness's mocked services and idealized movement explicit: even a full simulated match proves packaging and code-path behavior, **not** Studio playability. When the owner requests multiple builders, split independent modules (for example pure rules and client presentation) into non-overlapping staged directories with written APIs and acceptance tests; keep one integration owner for server glue, bots, full build, and Studio validation. Gate integration on verified module outputs rather than letting workers concurrently edit the same Rojo tree. For a large ordered upgrade of one existing Rojo tree, stage a clean tracked-source archive plus the full request into the isolated builder workspace; chain serial stage cards over that shared tree (each with a playable acceptance gate), then assign final host-side QA and authenticated publication to main. Do not treat queued stages or a running builder as completed implementation. Before dispatching a model-overridden builder, check its effective file/terminal tools and Docker backend with a small mounted-workspace probe; a configured toolset alone does not prove the runtime requirements are met. Repair a concrete prerequisite and resume the original card once, instead of removing isolation controls or duplicating the whole build task.
5. For shared physics, make the server create interaction targets and validate proximity, state, gate order, request rate, and completion. Test a client-owned object under handoff, latency, departure, and malicious transform; never award from a client claim or a touch alone. A server-observed speed check only rejects gross jumps, not gradual forged motion: describe that limit honestly. If ownership/correction is unreliable, reduce to a discrete or server-authoritative mechanic before expanding content.
6. Minimize the owner's manual Studio testing when possible. Check current [Studio MCP documentation](https://create.roblox.com/docs/studio/mcp) and the local Studio/MCP state first: Studio's built-in stdio MCP server can expose game-tree inspection, Luau execution, playtest control, simulated player input, viewport capture, and console output. Have the owner sign in himself and open the local `.rbxlx` place before looking for Assistant (the Studio start page does not show the editor toolbar); then enable **Assistant → ⋯ → Manage MCP Servers → Enable Studio as MCP server**. Connect Hermes to Studio's local `mcp.bat` as a stdio server, select only needed tools instead of enabling every discovered tool, and verify a real Studio instance plus `get_studio_state` and a known game-tree script before claiming access. A successful tool-discovery handshake alone does not prove that the place is reachable. Then run and log real engine tests rather than sending him an entire manual checklist. For an MVP surface restriction, inspect the exact rebuilt place in both menu and live states, including carrier and off-disc contextual hints; a hidden menu can still advertise or invoke excluded controls in gameplay. Reopen the place after a late HUD fix before claiming the final visual is checked. Preserve the canonical Rojo/Luau source when editing through Studio so Studio-only changes do not silently diverge. MCP runs against Studio on the same PC, not in the cloud: check current free memory and official Studio requirements before recommending multi-client tests; start with a solo test and reduce concurrent apps on a constrained machine. If Studio access is unavailable or too heavy, continue code-level tests without calling them engine validation, and give the owner exact local steps and a dated observation log for solo, two clients, empty server, handoff, non-carrier disruption, departure, teleport, network simulation, phone emulation, and physical phone where available. Distinguish emulator from real-device performance. Do not declare the technical gate passed until the engine observations exist; do not infer leaving motives from disconnects.
7. For a requested GitHub handoff, have the isolated builder deliver only source, built place, tests, and setup docs; main reruns checks and owns authenticated repository creation/push. For an existing repo, inspect open PRs and fetch the remote baseline before staging changes. Verify both source **and the tracked built `.rbxlx`** against the final tested workspace: compare all relevant source/project paths and hash the built place separately, then parse it and check that key new UI/scripts are packaged. A source-only push can leave GitHub's playable place stale even when every source file matches. If the local checkout is behind or has a modified place file, create a separate worktree from `origin/<base>` rather than pulling over it; copy the verified build there and open a focused PR. Verify the PR's exact remote-head file hash and changed-file list before saying the playable artifact is current. Distinguish GitHub source, GitHub built place, local checkout, Studio's open in-memory place, and the Roblox-published experience in status reports; none updates the next automatically. Leave the merge to the owner when requested, and report unrun checks explicitly. Report any unrun Studio/device cases separately from a successful merge. Give the repo a valid URL slug when the requested display name contains spaces, choose visibility explicitly, read back the remote and pushed files, and provide MacBook instructions for opening the included `.rbxlx` in Roblox Studio or rebuilding with Rojo. A Rojo build is not a Studio playtest; say which engine behaviors were actually exercised. Report each gate as completed/verified, evidence, uncertainty, tasks/outputs and money, recommendation, and next bounded task. Report the owner's dated human actions separately, not as agent hours. Do not contact minors directly, log PII, spend, buy assets, advertise, or publish a Roblox experience publicly without explicit authorization. Under-18 testing goes through a parent/guardian.

## Pitfalls
- Before merging a large staged upgrade, run an independent read-only source review (cowsearcher on a staged exact-commit tree plus the PR diff) and fix its blocking findings first. Headless mocks hide authority gaps such as accepting client-owned character positions without a per-heartbeat displacement cap; a self-written test suite and a passing gate do not substitute.
- Pin the merge to the reviewed head (`gh pr merge --match-head-commit <sha>`) and check the PR state first. If the PR already merged before late fixes were pushed, the fixes are not in the base: branch from the fix commit, open a follow-up PR, merge it, and confirm with `git merge-base --is-ancestor <fix-sha> origin/<base>`.
- Sync verified builder output into the canonical repo by copying only changed tracked files plus new evidence, then rerun the full suites in the repo itself (Docker, pinned tools) before committing. Worker-only artifacts (snapshot zips, request copies) stay out of the repo.
- A Studio window opened on the right path can still hold a stale in-memory place; compare its game tree with the build (for example, scripts under ReplicatedStorage) before treating MCP results as evidence. When automation cannot safely close or reopen it and free RAM is under about 1 GB, ask the owner to save, close, and reopen the built `.rbxlx`; do not kill the process.
- Reconcile integration evidence after every retained child patch: rebuild the place, rerun all suites, and hash the tested source/project/build bytes in one owner-run manifest. Older passing child manifests are snapshots, not evidence for the final tree.
- Test input suspension between render frames, not just after a render step; charge start/release must consult current menu, text-focus, liveness and help state. Test malformed envelopes against the shared server request budget before decoding action parameters.
- A stopped Docker Desktop Linux engine can suppress builder file/terminal tools. Check the daemon and mounted-workspace probe before changing provider or permissions; resume the existing task only after the prerequisite changes.
- A Docker builder's default PATH may omit the pinned Roblox binaries even when they are already mounted at `/workspace/_linux-roblox-tools/{lune,rojo,stylua,selene}`. Probe those absolute paths and versions in the same container before treating missing PATH entries as an installation blocker. After main-owned verification or a scoped follow-up patch, regenerate the full check log/build/hashes against the latest files; earlier green evidence does not cover later edits.
- Repeated Kanban blocks can auto-decompose a Roblox stage into parallel workers sharing one Rojo tree. Inspect parent/child edges and active claims before settling the original; retire redundant children, avoid concurrent edits, and give main ownership of the final verification rather than retrying a denied Builder shell step unchanged.
- For a main-only evidence gate after the next stage starts, verify a frozen ZIP/snapshot against every manifest SHA-256 before running checks. Translate container `cwd`, argv and artifact paths into host-side Docker invocations without changing source; keep Docker network available when Selene must fetch the Roblox API dump. `PASS_LOCAL` certifies only declared hashes/checks, never Studio feel or device/latency behavior.
- For a MacBook handoff of an included built place, lead with unzip → Roblox Studio → File/Open from File → Play. Rojo and Terminal commands are optional for rebuilding, not prerequisites for trying the `.rbxlx`.
- Keep a single canonical project folder even when isolated workers need staged copies; copy verified outputs back and do not present a worker scratch path as the deliverable.
- Check a Luau test's expected parameters before changing implementation after a red result; a contradictory assertion can masquerade as a code defect.
- Treat Studio's Network and Device simulators as separate evidence classes; the network simulator's presets and UI can change, so consult current Creator Hub instructions before giving exact menu steps.
- Distinguish an MCP connection check, a static source/test check, and a Play-mode engine test in every status report; each verifies a different layer, and an Edit-mode tree read does not prove gameplay.
- When live free memory is tight, measure it before launching Play or multiple clients; the MCP transport is lightweight, but Studio and client processes run locally and can freeze a constrained machine.
